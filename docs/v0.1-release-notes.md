# v0.1 — Bootloader-to-Application Jump

[← Back to main README](../README.md)

**Status:** Core jump mechanism working and verified on hardware.

## Overview

This is the first working milestone of the project: a bootloader that validates and jumps into an application flashed at a separate address, with correct vector table relocation on both sides. No firmware-update-over-UART yet — that's v0.2.

## Memory Map

| Region       | Address Range               | Size   |
|--------------|------------------------------|--------|
| Bootloader   | `0x08000000` – `0x08007FFF` | 32 KB  |
| Application  | `0x08008000` – `0x080FFFFF` | 992 KB |

Both regions have their own linker script with `FLASH` `ORIGIN`/`LENGTH` set accordingly, so each project's `.isr_vector` lands at the correct base address.

## How It Works

1. On reset, the bootloader runs first (its vector table is at `0x08000000`, the chip's default boot address).
2. The bootloader checks the application region for a plausible initial stack pointer value (a sanity check that an application is actually present) before attempting to jump.
3. If valid, the bootloader:
   - Disables interrupts and stops SysTick, so nothing fires mid-handoff using the bootloader's (soon to be stale) vector table.
   - Sets the Main Stack Pointer (MSP) to the application's initial stack pointer value.
   - Jumps to the application's reset handler address.
4. The application's own `SystemInit()` relocates `SCB->VTOR` to `0x08008000` (via `USER_VECT_TAB_ADDRESS` / `VECT_TAB_OFFSET` in `system_stm32l4xx.c`), so from that point on, all interrupts vector correctly into the application's own handlers.

## Hardware & Tools

- Board: NUCLEO-L476RG (STM32L476RG)
- IDE: STM32CubeIDE 2.1.1
- Flashing/debug: ST-Link (onboard), STM32CubeProgrammer
- UART: USART2 at 115200 baud, `printf` retargeted to UART via a custom `_write()`

## Debugging Notes (things that actually went wrong)

- **Boot loop caused by missing VTOR relocation.** The application's `system_stm32l4xx.c` ships with `USER_VECT_TAB_ADDRESS` commented out by default. Without it, `SCB->VTOR` is never updated after the jump, so every interrupt (SysTick included) keeps vectoring through the *bootloader's* vector table — which eventually faults and resets the chip, producing an infinite bootloader → app → bootloader loop on the UART log. Fix: uncomment `#define USER_VECT_TAB_ADDRESS`.
- **Silent/missing `printf` output in the application.** The application project didn't have UART peripheral init or a `_write()` implementation wired up, so `printf` calls had nowhere to go. Fixed by adding `MX_USART2_UART_Init()` and a `_write()` that routes through `HAL_UART_Transmit()`, matching the bootloader project's implementation.
